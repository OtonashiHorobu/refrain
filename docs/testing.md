# Testing

## Unit tests

The test binary uses Boost.UT and contains every suite in one process:

```bash
build/Release/bin/refrain-tests
```

Pass a suite name or a test name to run a subset:

```bash
build/Release/bin/refrain-tests "world/rwf"
build/Release/bin/refrain-tests --help
```

CTest runs the same binary:

```bash
ctest --preset conan-release --output-on-failure
```

World generation has data-driven cases that read the datapack from
`content/vanilla/<version>/data`. The datapack is not distributed; generate it
from a locally owned `server.jar` with `scripts/fetch-content.sh` as described
in [World generation data](worldgen.md). When it is absent, those cases are
skipped with a diagnostic.

## Configurations

The suite runs in more than one configuration because they do not agree about
what counts as an error.

```bash
cmake -S . -B build/debug -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=build/Release/generators/conan_toolchain.cmake \
  -DREFRAIN_DEBUG_ASSERTS=ON -DREFRAIN_LTO=OFF
cmake --build build/debug
build/debug/bin/refrain-tests
```

`-DREFRAIN_DEBUG_ASSERTS=ON` builds without optimisation and defines
`_GLIBCXX_ASSERTIONS`, so the standard library checks its preconditions: reading
the error of a successful `std::expected`, indexing a vector out of range or
using a disabled iterator aborts there instead of returning whatever the invalid
state holds. An optimised build compiles those checks away, which is why a
defect of that class passes every other gate; it is also the configuration that
catches a pointer handed to a C library that keeps it past the call, because the
bytes read back from a reused stack slot are stable enough to look correct once
optimised. It is still a CPU-bound suite, so the build is `-O0` and not a
sanitizer configuration.

`-DREFRAIN_COVERAGE=ON` instruments the same binary for gcov and lowers the
optimisation the same way. `scripts/dev/coverage.sh` drives the whole sequence
and writes `build/coverage-report/summary.txt`; set `REFRAIN_COVERAGE_MIN` to
fail under a threshold. Coverage is a local and scheduled measurement, never a
pull-request gate: the total is a weak signal, and the list of files no test
ever enters is the part worth reading.

## Continuous integration

```bash
scripts/ci.sh --offline
```

The pipeline checks, in order: vendored recipes against the lock, the platform
abstraction boundary, a lockfile-pinned Conan install, a full configure and
build, the unit tests, schema generation drift, the C ABI headers as C11, the
command-line contract, the runtime replay smoke, archive extraction, the crash
reporter smoke and `clang-format` over first-party sources.

`--skip-configure` and `--skip-build` reuse an existing build directory.

## Fixtures

All fixtures under `test/fixtures/` are synthetic or generated by the
repository tooling. The tree contains no game jars, extracted assets, world
saves or logs. Golden files under `test/fixtures/golden/` capture command
output and canonical file encodings; regenerate them with the documented
command in `test/fixtures/golden/README.md` when a deliberate output change is
made.

## Determinism

Tests that cover the simulation compare the state hash across two runs, or
across an encode and a decode. A change that alters the hash must come with a
format or behavior change that explains it.

## Fuzz smoke

`test/net/test_fuzz_smoke.cpp` feeds deterministic pseudo-random bytes to the
frame decoder (compressed and uncompressed), the text-component NBT decoder and
selected generated packet decoders. It runs in CI and asserts only that no input
crashes or hangs the decoder; malformed input is expected to return an error.

`test/net/test_fuzz_matrix.cpp` widens that to every serverbound decoder in the
schema: play, configuration and login. Each decoder sees random bytes, every
truncated prefix of a valid encoding and a byte-flipped copy, which is the shape
a truncated or corrupted client packet has. Adding a packet to the schema means
adding its decoder to that list.

## Protocol bot

`refrain-tools protocol bot` connects to an offline-mode server and walks the
handshake -> login -> configuration -> play sequence:

```bash
build/Release/bin/refrain-tools protocol bot \
    --host 127.0.0.1:25565 --username Bot --wait-chunks 1
```

`--wait-chunks` waits for that many chunk packets before reporting success;
`--command` sends a play command (for example `say hello`), `--wait-messages`
waits for system chat replies, and `--linger-ms` keeps the connection in play.
`--move-dx/--move-dy/--move-dz` move the bot relative to its spawn, with
`--move-delay-ms` / `--command-delay-ms` scheduling both actions.
The bot also performs the online-mode RSA/AES handshake; whether the session is
accepted is decided by the server's verifier.

### Packet capture

```bash
build/Release/bin/refrain-tools protocol capture \
    --host 127.0.0.1:25565 --out /tmp/join.rfcap
```

The tool records the clientbound packet bodies seen by the bot (state, packet
id, length, payload) in the RFCAP1 container. `--linger-ms` keeps recording
after the join, which is needed for packets sent after the first chunk. Compare
two captures by packet sequence with:

```bash
build/Release/bin/refrain-tools protocol diff \
    --left vanilla.rfcap --right refrain.rfcap
```

Captures are diagnostics and regression baselines; they contain no credentials.

### Load harness

```bash
build/Release/bin/refrain-tools protocol load \
    --host 127.0.0.1:25565 --bots 20 --duration-ms 5000
```

The harness opens N bots, keeps each in play for the duration and reports how
many joined. The server logs `runtime: <ticks> tick(s), avg <ms> ms, max <ms>
ms` on a clean shutdown, which is the baseline for MSPT checks.

`protocol load` opens one connection per bot. For runs beyond a few hundred
bots, `protocol pool-load` multiplexes every bot over one transport and one
timer thread:

```bash
build/Release/bin/refrain-tools protocol pool-load \
    --host 127.0.0.1:25565 --bots 1000 --duration-ms 60000 \
    --walk-radius 8 --walk-period-ms 100
```

It reports the joined count, join latency percentiles and packet counts, and
keeps each bot walking so the server exercises visibility and chunk streaming
under load. The shared transport keeps client-side memory and thread count
flat, which makes it the client to use when the measurement target is the
server.

### Load baseline

`scripts/soak.sh` prepares a world, starts the server on it, runs the load
client and prints one summary line per measurement:

```bash
scripts/soak.sh --bots 100 --seconds 120 --view-distance 6
```

By default the world is a synthetic anvil import. `--fresh` starts from an
empty world the server creates from `--seed`, so the run measures runtime
chunk generation against the tick budget instead of the storage path:

```bash
scripts/soak.sh --fresh --seed 99 --bots 20 --seconds 60 --view-distance 6
```

The fresh run also reports the spawn fill, the number of generator log lines
and how many connections finished their viewport. Its numbers depend on the
host's generator throughput; the reference below is the import baseline.

`--slow-clients N --read-delay-ms MS` adds a second cohort that refuses to read
at full speed, so its sockets stop draining and the transport's per-connection
write queue fills the way it does for a client on a bad connection. The delay is
per client, which is why the cohort is a separate load run:

```bash
scripts/soak.sh --fresh --seed 9 --bots 10 --seconds 40 --view-distance 6 \
    --slow-clients 1 --read-delay-ms 400
```

The run prints one `load:` line per cohort, so the throttled client's join
latency and chunk count are visible next to the normal bots'. It also prints a
`slow:` line only when the cohort exists.

The reference run uses 100 bots, a 6 chunk view distance and bots walking in an
8 block circle. On an Intel Core i7-10700K with the release build it reports:

```text
load: 100/100 joined packets=269209 chunks=400 join_ms p50=262 p99=281 max=281
soak: elapsed=125s
soak: shutdown=89ms
soak: server_peak_rss=48MiB
soak: bots_peak_rss=382MiB
soak: tick: 2480 interval=50ms missed=0 work_avg=1.79ms work_p99=3.51ms work_max=14.88ms samples=2048
soak: net: players=0 in=121498 out=271851 bytes_in=4335818 bytes_out=75668261
```

Read the numbers as follows:

- `work_p99` is the server tick work per 50 ms interval; `missed=0` means no
  interval overran its budget.
- `server_peak_rss` is the peak resident set of the server process, bots
  excluded.
- `out` and `bytes_out` are the clientbound packet count and payload over the
  whole run, so the 120 s run sends roughly 630 KiB/s to 100 players.
- `shutdown` is the time from the `stop` console command to process exit.

### Client input (X11)

Run the vanilla client under XWayland when a test needs real key/mouse input:

```bash
SDL_VIDEODRIVER=x11 MC_CLIENT_HOME=... MC_SERVER=127.0.0.1:25565 \
    scripts/dev/vanilla-client.sh
xdotool search --class com.mojang.minecraft windowactivate --sync
xdotool key e   # open the player inventory
```

This keeps the client unmodified; use it for manual inventory/click acceptance.
The native Wayland window does not accept `wlrctl keyboard type` as game input.

## Adding a suite

Create a file under the matching directory in `test/`, for example
`test/world/test_my_feature.cpp`, and define a `boost::ut::suite`. The CMake
build globs the directory, so no build file edit is needed. Prefer a negative
case over a second happy path.


## Acceptance

A change that touches the join path or the play loop is accepted against a real
client, not only against the protocol bot. The reproducible steps are:

1. `scripts/soak.sh --fresh --seed 99 --bots 20 --seconds 60
   --view-distance 6` proves the server creates a world from a seed, fills the
   spawn area, generates the viewport while the bots watch, accepts joins and
   shuts down cleanly. For a client join against an imported world, generate
   that world with `tools/make_test_world.py gen --chunks 256` rather than the
   default three-chunk fixture.
2. `refrain-tools protocol bot --host 127.0.0.1:25565 --username Bot
   --wait-chunks 1` proves the handshake, configuration and first chunks.
3. `MC_CLIENT_HOME=/path/to/26.3-runtime scripts/dev/vanilla-acceptance.sh
   --world /path/to/rwf-world` joins with the unmodified client through the
   acceptance agent in `tools/net/client-agent/`, which asserts the level load
   and writes a screenshot. A vanilla client also passes the checks listed in
   [running.md](running.md#client).
4. `refrain-tools protocol capture --host 127.0.0.1:25565 --out join.rfcap
   --wait-chunks 1` records the clientbound stream for a later comparison with
   `protocol diff` or the oracle below.

## Network oracle (optional, local)

`tools/net/oracle/` compares a capture from a locally owned vanilla 26.3 server
with a Refrain capture. It never downloads or commits server jars, assets or
captures. See [the oracle README](../tools/net/oracle/README.md).
